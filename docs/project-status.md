## 1. 台账用途与更新规则

本文件是项目唯一滚动进度台账。其他文档职责如下：

- 产品目标、P0/P0.5/P1/P2 和原始验收口径以 v2.1 产品方案为基线；
- [Direct 运行说明](arena-direct.md)记录当前可执行命令和技术边界；
- [2026-08-21 真实验收记录](arena-direct-acceptance-2026-08-21.md)只记录该次真实运行事实；
- [Direct-only 首版交付边界](arena-v0.md)记录收缩后的当前纵向切片；
- 本台账负责解释上述口径之间的差异，并维护当前进度、问题、决策和下一步。

更新本台账时遵循：

1. 不用单一百分比概括不同范围；分别报告 Direct-only 里程碑、v2.1 P0 和发布状态；
2. 区分“源码存在”“自动化已验证”“真实产物证明”“仅有日期验收记录”；
3. 未经产品负责人确认，不把范围延期自动写成从产品方案删除；
4. 技术 DNF、游戏内失败和平台故障分别记录，不用正常名次掩盖技术退出；
5. 每次真实比赛使用新的输出目录，旧 Replay 和报告不回填；
6. 任何 P0.5/P1/P2 扩展必须先更新本台账中的范围决策。

状态标记：

## 2. 总体结论

### 2.1 双口径状态

| 口径 | 当前状态 | 审计结论 |
| --- | --- | --- |
| Direct-only 最小闭环 | 已实现并完成一次真实纵向验收，存在已披露限制 | 四组独立配置、四请求 Probe、真实比赛、Replay/Trace/Report、单文件 HTML 和 Day 1～40 事实回放已经串通 |
| v2.1 完整 P0 | 部分完成，不能宣称验收通过 | strict MCP、采访、导演高光、娱乐解说、10 个奖项、6 类结局、完整 P0 看板和规定的样例场数量尚未完成 |
| P0.5/P1/P2 | 应继续冻结 | 动态幕、分享卡、多世界线、人格杯、自动播放、聚合榜单等尚不应抢占当前收口工作 |
| 仓库交付/发布 | 未完成 | Arena 代码、Web、测试、脚本、文档和产品方案大多仍未进入 Git 历史；本地产物位于被忽略的 `dist/` |

为避免把临时名称变成产品决策，本台账暂称已跑通的收缩范围为 **Direct-only M0**。是否保留该名称、改称 P0a，或正式改写 v2.1 P0，见 `DEC-001`。

### 2.2 是否跑偏

技术地基没有根本跑偏，以下方向与 v2.1 一致：

- Direct 是四 Agent 自动比赛的默认入口；
- 四槽位使用相同中性决策策略和无身份观察；
- 公共市场共享 seed，个人随机按槽位隔离；
- GameEnvironment、结构化事件、状态 diff、证据 ID 和 hash 构成事实链；
- 单 Agent 技术失败不阻塞其他 Agent，技术 DNF 不伪造正式名次；
- Replay 和单文件 HTML 可离线重建，正式页面缺 Replay 时失败关闭；
- 页面使用统一日期切片，第 40 天前不展示正式排名和最终运气审计；
- MCP 和叙事扩展的暂停避免了在真实比赛前继续扩张外围能力。

当前问题主要是**范围基线没有同步**：v2.1 仍把 strict MCP、采访、高光、解说、奖项和结局列为硬 P0，而当前 Direct-only 文档把它们延期。这个分叉属于已发生的实施顺序调整，不是代码错误；但若不形成正式产品决策，就不能同时声称“v2.1 P0 已完成”。

- Replay 能证明记录的 Provider/model/adapter 身份和请求结果，但单靠 Replay 不能证明 Adapter 一定连接真实外部服务而不是测试替身；Runner 自身也明确披露此限制。
- CLI 要求四套独立配置，但当前只强制 slot/id 唯一，不强制四个 Provider 或 model 彼此不同。本次真实配置确实不同，不等于代码已把“四个不同模型”固化为不变量。

## 8. 需要产品负责人确认

本节只登记问题，不代表已经决定。建议按顺序确认。

### DEC-001：当前范围基线

选择其一：

1. v2.1 保留为完整产品蓝图，当前收缩范围正式命名为 Direct-only M0/P0a；
2. 正式修订 v2.1，把 strict MCP 和叙事模块移出 P0；
3. 继续沿用两套未命名口径。

审计建议采用第 1 项：既保留产品北极星，也如实承认当前只完成基础纵向闭环。第 3 项风险最高。

### DEC-002：strict MCP 的长期位置

确认 strict MCP 是：

- 仅退出 M0、仍属于后续 P0；
- 移入 P1；
- 长期取消，仅保留 legacy MCP。

当前实现只支持“占位且不伪装已完成”。

### DEC-003：娱乐化下一步

真实比赛已经跑通并实际观看，原“先暂停外围能力”的前置条件已经满足。需要确认下一阶段是：

- 继续只做事实型 Runner/Replay；
- 回到娱乐化产品目标，优先加入程序化、证据驱动的导演高光；
- 优先采访、奖项或结局；
- 继续整体冻结叙事层。

若恢复娱乐化，审计建议先做不调用模型的程序化高光和关键事件横向对比，再评估采访与 LLM 文案。

### DEC-004：v2.1 样例验收门槛

确认是否保留“1 场 Scripted + 3 场 Direct + 1 个 strict MCP episode”的 P0 金样要求，以及技术 DNF 是否允许作为解释充分的有效样例。

当前只能确认一条真实 Direct 闭环，不能确认 v2.1 P0 样例验收完成。

### DEC-005：模型杯展示身份

确认模型杯采用：

- 中性 A/B/C/D + Provider/model；
- 仅 Provider/model；
- 继续保留策略化展示名，但明确标注为纯视觉身份。

当前 Prompt 是中性的，但固定名称和 personaId 仍带有策略含义。

### DEC-006：技术 DNF 与运气标签

确认技术 DNF：

- 不参与“最幸运/最倒霉”；
- 按参赛天数归一化后参与；
- 保留原始计数，但删除价值判断标签；
- 维持当前规则。

### DEC-007：正式 Benchmark 的 slot 公平

若未来发布模型能力结论，需要确认多 seed 下是否轮换模型与 A/B/C/D slot。当前单场只适合作为受控展示赛。

### DEC-008：下个审计里程碑字段

确认是否要求下个里程碑补齐：

- 版本化上下文策略和完整发送上下文 hash；
- model revision 与 sampling parameters；
- 总墙钟上限；
- 请求与 action 的逐条关联；
- 平台/Provider/模型故障责任归属；
- 成本。

成本需另行确认 `unavailable` 是否满足 M0，还是必须使用版本化价格快照计算。

### DEC-009：是否运行 `run-002`

确认是否需要一场使用延迟统计修复后代码的新真实比赛，以及验收目标是：

- 只验证 post-fix 报告；
- 要求四个 Provider 都无技术 DNF；
- 要求四个 Agent 都存活到 Day 40。

后两项是不同目标：游戏内死亡是合法结果，不能与 Provider 稳定性混为一谈。任何新比赛都需要新的在线调用授权和输出目录。

### DEC-010：交付目标

确认下一交付是：

- 仅本地研究和演示；
- 可审查的 Git 提交；
- 私有仓库协作；
- 公开仓库、页面或线下对外展示。

公开交付会触发 GPL、依赖许可证、模型厂商名称、生成素材和内容传播审查。

### DEC-011：技术选型是否为强制约束

确认 v2.1 中 ECharts、Vitest、Playwright、CSS Modules 和 Reducer/Context 是推荐方案还是硬要求。当前轻量替代实现尚未造成明确功能失败，但自动浏览器覆盖明显少于原测试计划。

### DEC-012：四 Provider 是否必须由代码强制不同

确认“四组独立配置”是否足够，还是模型杯必须在 CLI 层拒绝重复的 Provider/model 组合。

### DEC-013：Probe 与原始交换记录留存

确认：

- Probe 是否应显式输出可选 JSON 文件；
- 原始请求/响应是否继续默认不保存；
- 脱敏诊断的保存目录、权限、保留周期和是否属于正式验收包。

审计建议正式 Replay 继续不保存原始交换；若需要审计，使用显式开启、脱敏、Git 忽略且有限保留期的独立诊断产物。

## 10. 待确认后的建议顺序

本节是审计建议，不代表已经授权实施：

1. 先确认 `DEC-001`～`DEC-005`，形成唯一 P0/M0 范围口径；
2. 只做文档收口：修正 `CLAUDE.md`、`web/ASSETS.md`、`web/design-qa.md`、README 和 package 元数据的现状描述；
3. 完成 Git 提交边界审查，排除 `.DS_Store`、未批准素材和无关删除；
4. 若保留 Benchmark 方向，先补版本化上下文审计、revision/sampling、总墙钟和故障归属；
5. 若需要真实稳定性验收，先重新 Probe，再使用新目录运行 `run-002`；
6. 若恢复娱乐化，先实现程序化高光和关键事件横向对比，再决定采访、奖项、结局和 LLM 解说；
7. strict MCP 只在产品负责人确认其里程碑后进入实现，不应与当前 Direct 稳定化并行扩张。
